# ZWSO Methodology v0.3 . Context-conditioned decision corpus

## Purpose

ZWSO v0.3 preserves the weekly immutable world-state archive while adding two downstream capabilities:

1. a broader, rights-aware public-source sensing layer; and
2. a context-conditioned question pipeline for forecasting, life decisions, reasoning and practical judgment.

The core distinction is:

- **evidence layer:** what was externally observable at time `t`;
- **question layer:** what decision or forecast is being tested independently of the world state;
- **modulation layer:** whether and how the answer should change when a defined ZWSO context is supplied.

ZWSO is not an oracle and does not provide a single authoritative answer. It preserves contextual evidence, disagreement, uncertainty and provenance so downstream systems can test context sensitivity rather than infer it retrospectively.

## Two-layer question structure

Every context-conditioned item starts from a stable question kernel.

### Layer A . Baseline

Ask the underlying question without ZWSO context.

Example form:

> You have limited cash and two possible investments. One is higher return but harder to reverse. What information would you want before deciding?

### Layer B . ZWSO-conditioned

Ask the same underlying decision after adding only decision-relevant facts from one immutable context packet.

Example form:

> Same decision. In this ZWSO context, borrowing costs are rising, consumer confidence is falling and demand volatility has increased. What changes in your decision, if anything?

The pair is labelled with one of:

- `CONTEXT_SENSITIVE` . the supplied world state should rationally change the answer or probability;
- `CONTEXT_INVARIANT` . the context is noise or should not change the underlying judgment;
- `UNKNOWN` . evidence is insufficient to specify the expected relation.

This creates a measurable **context elasticity** signal: not merely what an answer is, but whether a human or model changes it when the external state changes.

## Optional counterfactual layer

A later experiment may present the same kernel under two historical or synthetic ZWSO contexts. This is useful for robustness, regime-change and hindsight-bias testing. Counterfactual contexts must be labelled and must never be mixed with contemporaneous records.

## Source expansion

v0.3 expands sensing beyond conventional news while retaining the four v0.2 source families. New adapters are catalogued with access mode, cadence, rights class and training-use status.

### News and events

- GDELT DOC / Context APIs for multilingual news salience and divergence.
- selected regional, local and public-agency RSS/Atom feeds to reduce major-outlet and Anglosphere bias.

### Public attention, culture and behaviour

- Wikimedia Analytics for pageview/edit attention signals.
- Bluesky Jetstream for aggregate public-discourse velocity.
- Hacker News public feed for technical/entrepreneurial discourse.

User-generated content is treated as a signal source. Public availability does not imply permission to place verbatim user text into a model-training corpus.

### Science and technology

- Crossref metadata for publication flow, topics, funding and post-publication updates.
- arXiv metadata for early research movement.
- GitHub Events for aggregate builder activity and repository/topic movement.

### Slow reality

- World Bank Indicators for long-horizon development and economic measures.
- FRED/ALFRED for macroeconomic series and data vintages, subject to series-level rights review.
- WHO current data interfaces for health state.
- CISA Known Exploited Vulnerabilities for operational cyber-risk deltas.

### Forecasting references

Forecasting platforms may be used only within their terms. Metaculus is explicitly marked `EXCLUDED` from the training pipeline unless written permission covers the intended AI/ML use. It may still be used as an external forecasting reference or evaluation surface when permitted.

## Source balancing

Firehose volume must not determine ZWSO importance.

A high-volume social stream cannot drown out a low-frequency inflation release, outbreak report or regulatory change merely because it produces more records. Synthesis must preserve source-family balance and report disagreement between:

- event/news salience;
- public attention or attitude measures;
- cultural/behavioural signals;
- slow measured reality;
- specialist/research signals where relevant.

The unit of synthesis is a **signal**, not a post or article count.

## Data flow

```text
public sources
    ↓
source_catalog
    ↓
source_observations
    ↓
normalization + derived signals
    ↓
weekly immutable snapshot / significant delta
    ↓
context_packet
    ↓
question_generation_queue
    ↓
Layer A baseline + Layer B context-conditioned variant
    ↓
review / provenance / rights gate
    ↓
Pukot question delivery
    ↓
paired responses + later outcome
    ↓
training/evaluation corpus when explicitly eligible
```

Raw firehose records do **not** automatically become training examples.

## Context packet

A context packet stores:

- `context_key`
- `as_of`
- coverage window
- state vector
- salient themes
- shocks
- persistent signals
- weak signals
- source-family and regional divergence
- unknowns
- confidence
- source mix
- evidence references
- freshness state

Weekly snapshots remain the canonical temporal anchors. Significant between-snapshot deltas may create additional packets, but must never overwrite a weekly record.

## Question generation

Each eligible context packet is paired with active Pukot question kernels. Generation must:

1. preserve the underlying construct being tested;
2. create a baseline and context-conditioned form;
3. use only decision-relevant context facts;
4. preserve action symmetry and avoid answer-leading framing;
5. record whether context sensitivity is expected;
6. preserve evidence lineage;
7. avoid copying source prose into the generated question;
8. remain `DRAFT` and training-ineligible until reviewed.

Useful question families include:

- probability and forecasting;
- resource allocation;
- reversible vs irreversible decisions;
- trust and evidence thresholds;
- career and business decisions;
- cooperation vs independence;
- timing and optionality;
- risk under uncertainty;
- communication and coordination;
- everyday practical choices;
- identifying when world context is irrelevant.

The final category is important. The system must learn not only when context matters, but when it should be ignored.

## Training semantics

There are four distinct objects that must not be conflated:

1. **raw evidence** . source material or source metadata;
2. **derived signal** . a normalized observation, trend, delta or aggregate;
3. **question artifact** . a synthetic baseline/context pair derived from signals;
4. **training example** . a reviewed question artifact plus response/outcome explicitly marked eligible.

A source can therefore enrich ZWSO without its underlying text ever entering a training dataset.

Training eligibility requires:

- source-rights status compatible with the use;
- provenance retained;
- no sensitive/private source leakage;
- review status `APPROVED`;
- explicit eligibility on both the question artifact and response;
- synthetic/counterfactual material clearly labelled;
- historical context distinguished from contemporaneous context.

## Evaluation

v0.3 should eventually measure:

- **context elasticity:** how much answers/probabilities move between layers;
- **appropriate invariance:** whether irrelevant context is correctly ignored;
- **calibration:** whether context-conditioned forecasts resolve better;
- **regime robustness:** whether a reasoning pattern survives different historical contexts;
- **hindsight resistance:** whether later information contaminates reconstruction of earlier decisions;
- **source sensitivity:** whether answers are dominated by one source family;
- **human/model divergence:** where humans and models react differently to the same contextual shift.

## Current implementation

The structured schema contains:

- `zwso.source_catalog`
- `zwso.source_observations`
- `zwso.context_packets`
- `zwso.question_generation_queue`
- `zwso.question_context_variants`
- `zwso.question_context_responses`
- `zwso.v_training_question_pairs`

Existing structured weekly snapshots are backfilled as context packets. New eligible context packets automatically enqueue paired-question generation against active Pukot question kernels.

The existing GitHub ↔ structured-database freshness issue remains separate and must still be resolved. Public snapshots that have not reached the structured ZWSO store must not be silently treated as available structured context.
